# Delegation architectures for autonomous orchestrators

## 1. Which control-flow mechanisms are genuinely different?

### Takeaway

The important distinction is **who owns continuation**, not the agent brand: a manager awaits a bounded child result; a handoff changes the active conversation owner; a supervisor repeatedly selects workers; a workflow runtime schedules graph nodes; or independently addressed agents exchange messages. A hierarchy is a composition of these mechanisms, not a separate durability guarantee.

Research reference date: **2026-11-09**. Sources below are official documentation, official repositories, or their source files. Undated living documentation was retrieved for this research; publication dates and exact release dates were not established. Context7 was used for every framework's API/usage claims, with primary pages/source used to resolve details. No execution benchmarks or production reliability measurements were collected.

### Cited Findings

| Mechanism | Concrete implemented control flow | Context/result boundary | Decision authority and tradeoff |
| --- | --- | --- | --- |
| **Manager / agents as tools** | OpenAI `Agent.as_tool()` starts a nested specialist run, returns its result as a tool response, and resumes the manager. It does **not** transfer user-facing ownership. | Nested input is explicit; structured tool parameters and a custom output extractor can constrain the boundary. Manager combines results. | Model chooses whether/which registered specialist tool to invoke. Good bounded delegation and centralized policy; adds manager turns and a synthesis bottleneck. [OpenAI orchestration](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md), [tool contracts](https://github.com/openai/openai-agents-python/blob/main/docs/tools.md). |
| **Handoff / swarm routing** | OpenAI handoff switches the active agent; the specialist owns the remainder of the turn. Each registered handoff has a destination; custom handoff code can select a target at invocation time. | Full preceding conversation is visible by default; `input_filter` changes what the destination sees. Handoff input arguments are metadata for the handoff callback, not automatically a replacement for conversation history. | Model chooses an allowed transfer; destination runs with its own instructions. Good conversational specialization, not intrinsically a spawned child with a future/result join. [Handoffs](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md). |
| **Supervisor / worker selection** | Microsoft Agent Framework group chat has an orchestrator that selects the next speaker; handoff instead lets participants choose the next target. Magentic adds a task ledger and progress ledger, chooses a speaker/instruction, detects stalls, and replans. | Supervisor retains team history/planning state; worker output feeds the next selection. | Model-driven recurring dispatch among configured participants, unlike a fixed pipeline. Better adaptive sequencing, but manager judgments and stop rules are additional failure points. | **Hierarchical teams** | CrewAI `Process.hierarchical` gives a manager responsibility for delegation and review over a supplied crew/task list. LangGraph subgraphs can contain their own orchestration and route back to the parent with `Command.PARENT`. | CrewAI task context and outputs; LangGraph explicit state schemas and parent reducers for shared keys. | Delegation can be model-decided inside a code-defined team. More levels permit specialization but introduce extra context compression/coordination boundaries. CrewAI explicitly documents logical sequential task progression even in hierarchical mode. [CrewAI hierarchy](https://docs.crewai.com/en/learn/hierarchical-process), [LangGraph parent routing](https://docs.langchain.com/oss/python/langgraph/graph-api-send-command). |
| **Graph / workflow / dynamic fan-out** | LangGraph edges and conditional edges schedule nodes. `Send(node, input)` launches a runtime-sized set of worker invocations; reducers collect results for synthesis. ADK `SequentialAgent`, `ParallelAgent`, and `LoopAgent` execute configured subagents in order, concurrently, or repeatedly. | LangGraph worker-specific input and explicit shared-state reducers; ADK branch-local history but shared session state in parallel branches. | The graph/agent classes are code-defined. A model-generated work list can determine how many `Send` invocations occur, but fixed `ParallelAgent` execution alone is not autonomous delegation. [LangGraph Send](https://docs.langchain.com/oss/python/langgraph/graph-api), [worker example](https://docs.langchain.com/oss/python/langgraph/workflows-agents), [ADK parallel source](https://github.com/google/adk-python/blob/main/src/google/adk/agents/parallel_agent.py), [ADK loop source](https://github.com/google/adk-python/blob/main/src/google/adk/agents/loop_agent.py). |
| **Message bus / event-driven actors** | AutoGen Core `send_message` addresses an `AgentId` and awaits the handler's returned response; `publish_message` fans out to topic subscribers and expects no response. Runtime instantiates registered agent types on first delivery to a new identity. | Typed message classes, agent-private state, subscriptions/topic keys rather than mandatory shared transcript. | Application code or a model-backed handler may decide what to send next. Looser coupling and independent identities, but joins, correlation, timeouts and termination must be designed. [Messaging semantics](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/framework/message-and-communication.html), [lifecycle](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/core-concepts/agent-identity-and-lifecycle.html). |
| **Shared-state / blackboard-like coordination** | LangGraph nodes update a common typed state through reducers. CrewAI Flow methods listen for predecessor outputs and mutate shared state; routers select continuation paths. | Shared facts/results rather than passing an entire transcript at every hop. | These are usable blackboard-like building blocks, **not evidence of a built-in autonomous knowledge-source arbitration blackboard**. Graph edges/listeners still decide when work executes. [LangGraph graph/state API](https://docs.langchain.com/oss/python/langgraph/graph-api), [CrewAI Flows](https://docs.crewai.com/en/concepts/flows). |

Additional distinctions:

- **Static topology is compatible with dynamic decisions.** OpenAI tools/handoffs and ADK `sub_agents` usually enumerate available specialists in code; choosing one dynamically does not mean creating a new role or process. LangGraph `Send` dynamically creates invocations of a named, already-defined node, not arbitrary newly generated executable agents. AutoGen's lazy instances are created from registered types. [OpenAI handoffs](https://github.com/openai/openai-agents-python/blob/main/docs/handoffs.md); [LangGraph Send](https://docs.langchain.com/oss/python/langgraph/graph-api); [AutoGen lifecycle](https://microsoft.github.io/autogen/stable/user-guide/core-user-guide/core-concepts/agent-identity-and-lifecycle.html).
- **ADK now has multiple child-call contracts.** Current repository docs recommend `mode="single_turn"` subagents where supported: events remain in a branch of the parent's session, with tool-input-only context by default and optional parent history. `AgentTool` instead creates a separate disposable session, never copies parent conversation, returns only the final answer, but copies state changes back and shares artifacts/services. This is conversation isolation, not side-effect isolation. [ADK AgentTool guide](https://github.com/google/adk-python/blob/main/docs/guides/tools/agent_tool/index.md).
- **ADK transfer and task completion are different.** `transfer_to_agent` changes conversation ownership within the allowed tree; parent/peer transfers can be restricted. A documented remote A2A task-mode child can interact over multiple turns and completes only with `finish_task`, not merely because it emits a response. [Transfer event actions](https://github.com/google/adk-python/blob/main/docs/guides/events/event_actions/index.md); [transfer target source](https://github.com/google/adk-python/blob/main/src/google/adk/flows/llm_flows/extensions/_agent_transfer.py); [remote task-mode completion](https://github.com/google/adk-python/blob/main/docs/guides/agents/remote_a2a_agent/task.md).
- **Frameworks expressly separate code control from model control.** OpenAI describes both LLM orchestration and code orchestration. Microsoft describes workflows as explicit execution paths. CrewAI flows are event/listener routing around crews; neither a fan-out diagram nor multiple model calls alone establishes model-decided delegation. [OpenAI multi-agent guide](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md); [Microsoft overview](https://learn.microsoft.com/en-us/agent-framework/overview/); [CrewAI Flows](https://docs.crewai.com/en/concepts/flows).

### Inferences

- For Starfleet, compare **manager-owned bounded tasks**, **supervisor-led iterative teams**, and **durable graph tasks** as primary options. Treat peer handoff as a separate interface-routing capability rather than the default autonomous work scheduler.
- Hierarchy should be justified by a useful context/security/ownership boundary, not by mimicking an organization chart.
- A shared blackboard may reduce transcript forwarding, but needs provenance, versioning, conflict handling and scheduling policy; “shared dictionary” is insufficient.

### Gaps

- No evidence here establishes an out-of-the-box decentralized blackboard scheduler with durable claims/leases and automatic conflict resolution across these systems.
- No selected source establishes unrestricted recursive model-created agent types, processes or compute resources as a default capability. Do not equate runtime invocation fan-out with arbitrary spawning.

## 2. How do contracts, child lifecycle, waits, durability, retries and cancellation work?

### Takeaway

Conversation persistence, resumable control state, and a durable distributed scheduler are different layers. Strongest concrete evidence in this review is LangGraph's checkpoint/replay semantics, ADK's call-ID-based long-running resumption, CrewAI's event-triggered snapshots, and Microsoft/OpenAI integrations with dedicated durable execution systems—not a claim that every agent call is automatically a durable job.

Important source conflicts and cautions:

- CrewAI Context7 results include older `inputs={"id": ...}` resume examples, while versioned newer guidance marks that form deprecated and recommends `restore_from_state_id` for **forking**. Neither should be casually described as exact continuation. Use current full checkpoint documentation when comparing recovery semantics. [Versioned deprecation guidance](https://docs.crewai.com/v1.15.2/en/guides/flows/inputs-id-deprecation); [current checkpoint reference](https://docs.crewai.com/en/concepts/checkpointing).
- ADK's current docs distinguish single-turn subagents from disposable-session `AgentTool`. Describing every ADK subagent as sharing the same conversation, or every tool-agent as fully isolated, is incorrect. [Current AgentTool comparison](https://github.com/google/adk-python/blob/main/docs/guides/tools/agent_tool/index.md).
- A timeout/iteration limit is not a correctness condition: ADK `LoopAgent` marks completion when its max iteration count is exhausted without validating the work; Magentic can terminate for reaching round/reset limits. [ADK loop source](https://github.com/google/adk-python/blob/main/src/google/adk/agents/loop_agent.py); [Magentic source](https://github.com/microsoft/agent-framework/blob/main/python/packages/orchestrations/agent_framework_orchestrations/_magentic.py).

### Inferences

- Candidate Starfleet task envelope: task/parent IDs, objective, permitted tools/resources, input artifact references, context budget, output schema, acceptance evidence, deadline, retry policy, idempotency key, cancellation state and terminal reason. This is a **research recommendation**, not an existing universal framework contract.
- Separate **execution completed**, **output schema valid**, **acceptance checks passed**, **budget exhausted**, **canceled**, and **failed**. A child returning fluent text or reaching a stop limit should not certify success.
- For durable children, prefer externalized artifacts and small durable correlation/state records over repeatedly copying full transcripts into a scheduler's event history.
- Cancellation needs two scopes: stopping compute and controlling already-started external side effects. None of the reviewed cancel APIs by itself establishes rollback of external effects.
- Research should fault-inject parent crash, child crash, sibling partial failure, duplicate delivery, late result after cancellation, and checkpoint-write failure. Different semantics above predict materially different outcomes.

### Gaps

- No uniform cross-framework policy for parent cancellation cascading to all descendants, orphan cleanup, retries of non-idempotent tools, global concurrency budgets or child leases was established.
- Do not rank reliability from feature checklists: no comparable measured recovery rate, duplicate-side-effect rate or long-horizon success data was collected.
- Microsoft hosting details differ by Python/.NET and extension versus in-process runtime. The .NET superstep implementation is not evidence of identical Python internals.
- Current source branches and living docs are not pinned release artifacts. Implementation/API availability must be checked against a selected release before adoption.

## 3. What is current, and what options should Starfleet investigate?

### Takeaway

Legacy OpenAI Swarm and Microsoft AutoGen should be architecture references, not assumed current framework choices. Investigate a hybrid: model-selected bounded delegation under an explicit, durable execution/approval layer; retain handoffs and event buses only where their different ownership semantics are actually useful.

### Cited Findings

- **OpenAI Swarm status:** repository explicitly says experimental/educational, replaced by the production-oriented OpenAI Agents SDK, and recommends migration for production. Its historical loop is completion → tools → optional active-agent switch → context update; it stores no state between calls. No archive date was established. **Evidence: high, official README.** [Swarm repository](https://github.com/openai/swarm).
- **OpenAI Agents SDK:** maintained successor identified by Swarm; current repository docs distinguish agents-as-tools and handoffs and link durable execution integrations. No latest version is claimed here. **Evidence: high for documented status and architecture, not independently measured production quality.** [Swarm migration notice](https://github.com/openai/swarm); [Agents orchestration](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md); [durable execution links](https://github.com/openai/openai-agents-python/blob/main/docs/running_agents.md).
- **AutoGen status:** retrieved official README now prominently says **archived and no longer maintained**, with no Microsoft bug/security fixes, and directs users to Microsoft Agent Framework. Lower in the same README, stale wording still says maintenance mode/community-managed; that conflicts with the prominent archive notice and should not override it. Exact archive date was not established. **Evidence: high for current explicit notice; internal documentation inconsistency recorded.** [AutoGen repository](https://github.com/microsoft/autogen).
- **Microsoft Agent Framework status:** AutoGen's notice calls MAF 1.0 a production-ready successor; current MAF README presents .NET/Python production-oriented agents/workflows and a separate Durable extension. Microsoft Learn describes MAF as the direct successor to AutoGen and Semantic Kernel. Treat “production-ready” as a vendor status assertion, not a measured reliability guarantee. No latest patch number or release date is inferred. **Evidence: high for successor direction, medium for maturity marketing.** [AutoGen notice](https://github.com/microsoft/autogen); [MAF repository](https://github.com/microsoft/agent-framework); [overview](https://learn.microsoft.com/en-us/agent-framework/overview/); [durable extension](https://github.com/microsoft/agent-framework-durable-extension).
- **LangGraph, CrewAI, ADK current surfaces:** the retrieved official docs/source contain dynamic worker dispatch/checkpointers, full event-driven checkpoints, and resumable agent/session lifecycles respectively. Context7 indexed multiple historical versions; those lists are not used as proof of latest versions or release dates. **Evidence: high for documented capabilities, release-specific availability unverified.** [LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api); [CrewAI](https://docs.crewai.com/en/concepts/checkpointing); [ADK](https://github.com/google/adk-python/blob/main/docs/guides/apps/resumability/index.md).

### Inferences

**Options for research, not implementation approval:**

1. **Bounded delegation manager:** one orchestrator calls specialists as tools with scoped context and schema/evidence contracts. Research whether context savings and independent verification outweigh added manager calls. OpenAI agents-as-tools and ADK single-turn/AgentTool make the contract especially concrete.
2. **Durable graph spine with adaptive fan-out:** code fixes approval gates, resource limits and lifecycle rules; a model proposes tasks and worker selection; a runtime performs dispatch/join/checkpointing. LangGraph `Send` and Microsoft workflows/durable extensions are concrete precedents. Best fit to compare when restartability and explicit gates are requirements.
3. **Hierarchical supervisor teams:** domain supervisors own bounded subplans and feed structured evidence to a top-level manager. Compare only when problem decomposition genuinely needs multiple levels; measure repeated planning, context loss and contradictory acceptance decisions.
4. **Event-driven worker fabric:** addressed workers plus result events support asynchronous external work and separate process placement. Research task correlation, durable delivery, leases, duplicate suppression, joins and cancellation explicitly; AutoGen's architecture illustrates message semantics but its archived runtime is not the recommended adoption target.
5. **Conversational handoffs:** useful for a specialist owning interaction, clarification and continuity. Do not use a transfer primitive as a substitute for a child task handle if the orchestrator must later collect results and continue independently.

**Decision variables to bring to a Starfleet gate:** who can create child tasks; who chooses worker type; whether children can spawn descendants; which context is copied versus referenced; required output/evidence schema; scheduler versus model ownership of joins; persistence and replay boundary; crash and duplicate-side-effect tolerance; retry budget; cancellation propagation; approval boundary. These are recommended evaluation questions, not verified Starfleet requirements.

**Recommended comparison experiment:** hold model, task set, tools and total budget constant; compare (a) single agent, (b) manager with bounded specialists, and (c) the same specialists under a durable graph. Measure correct completion, wall time, tokens/cost, supervisor overhead, duplicate work, recovery after crash and human interventions. This isolates mechanisms instead of comparing framework brands with uncontrolled defaults.

### Gaps

- Starfleet code/architecture was intentionally not inspected for this research assignment; implications are candidate options, not repository-specific implementation proposals.
- No future releases are predicted. Exact latest package versions, archive dates, and release-pinned feature compatibility remain to verify before any implementation choice.
- Sources are linked inline at claim granularity; repeated URLs deliberately retain a direct audit trail. Official documentation/source proves semantics, not comparative efficacy.
